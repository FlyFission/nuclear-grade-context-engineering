# Statistical Analysis — Read This Before Trusting Any Single "WINS"

This document exists because an adversarial review of the plan to fix this
project's own self-audited gaps predicted, before any number was computed,
that formal significance testing would show close to nothing survives at
this sample size — and that a p-value column risks *looking* more rigorous
than the underlying evidence actually is. Both predictions were confirmed.
Read the table below as the finding, not the prose around it.

## Headline result

**Of 47 statistical tests run (one per skill per round, the 3
`reviewing-code-quality` tasks, and the 3 closeout rechecks that decided a
final WINS status for `briefing-an-agent`, `proving-claims`, and
`creating-change-records`), zero survive Benjamini-Hochberg
false-discovery-rate correction at α=0.05.** This includes the single
strongest results in the entire project. (An earlier version of this
document covered only 44 tests, omitting the 3 closeout rechecks below —
Codex review caught the omission; adding them changes the correction's
per-test BH-adjusted values but not the headline conclusion.)

Full 47-row table in `data/statistical-analysis/statistical_summary.json`,
generated by `scripts/compute_stats.py` (no scipy in this environment; Fisher's
exact test is implemented directly via the hypergeometric distribution using
`math.comb`, verified against the known reference value for a 3-vs-0-of-3
split before trusting it on real data — see the script's own inline check).

**A note on independence within this family, disclosed rather than
smoothed over:** `briefing-an-agent`'s closeout row is a genuinely fresh
scenario (a true-niche regression check run after the amendment). The
`proving-claims` and `creating-change-records` closeout rows are
re-gradings of the *same* Gate 1 transcripts already counted separately
above, scored against a corrected, narrower criterion — not independent
new samples. Multiple-comparisons correction still treats each as its own
reported test (that is what the correction is protecting against: the
number of conclusions being drawn, not just the number of independent
coin flips), but a reader should know two of these three rows share raw
data with rows already in the table above.

**What this means, stated plainly:** at n=3–5 per cell, this project cannot
formally rule out chance for any individual skill once you account for having
run ~47 tests. This is not a claim that the effects are fake — a 5-vs-0 split
is a real, large, directionally consistent pattern, and the manually-verified
transcripts behind several of these results (see `GATE1_REPORT.md` section 3,
`AMENDMENT_VALIDATION.md`) show real behavioral differences a human reading
the raw text can see for themselves. It means the *statistical* layer of
evidence is weak, on top of — not instead of — the direct-inspection layer.
**Treat every "WINS" label anywhere in this project as a directional,
pilot-level finding, not a statistically proven effect**, until sample sizes
increase by roughly an order of magnitude (n≈30+ per cell would be needed to
plausibly clear correction for a 0.15–0.20 point effect at this base rate).

## Why the p-value column doesn't fix the underlying problem

Adding this table does not change any of the following, and should not be
read as if it does:

- It does not make n=3–5 into a larger sample.
- It does not resolve non-independent scenario/criteria authorship (see
  `REPORT.md` section 2 and `README.md`'s self-audit).
- A p-value near the 0.05 uncorrected line is exactly as easy to overread as
  the case counts it replaces — "p=0.048" reads as more authoritative than
  "4 out of 5," even though at this n they carry the same information.

## Pre-calibration desk audit — free, from data already collected

Separately: the self-audit flagged "no pre-calibrated task difficulty" as a
gap, alongside SkillsBench's practice of measuring baseline performance
*before* finalizing a task and only keeping tasks where it's low. This can be
partially checked for free against round 1's own data, no new trials needed.

**17 of the 27 round-1 scenarios (63%) had a `without_skill` baseline success
rate at or above 50%** — the threshold this project's own amendment plan
proposed adopting from SkillsBench:

| Baseline rate | Count | Skills |
|---|---|---|
| 100% (3/3) | 12 | `briefing-an-agent`, `checking-legal-and-safety-wording`, `checking-release-readiness`, `checking-what-a-change-affects`, `creating-change-records`, `deciding-who-decides`, `proving-claims`, `rating-change-risk`, `recording-what-an-agent-did`, `responding-to-incidents`, `stress-testing-agent-changes`, `vetting-outside-code-and-models` |
| 67% (2/3) | 5 | `breaking-down-the-work`, `checking-source-claims`, `double-checking-before-acting`, `questioning-attitude`, `staying-on-mission` |

Under a pre-calibration protocol, all 17 of these scenarios would have been
flagged for redesign *before* any `with_skill` trial was ever run — not
discovered as ceiling effects after the fact, which is what actually
happened and is why Gate 1 existed as a second round at all. This is stated
here as a completed, free retrospective check, not a new finding requiring
new trials: **the answer was already sitting in `REPORT.md`'s own summary
table.** The 5 "thin-margin" wins specifically (67% baseline) are a subset of
this larger 17-scenario group, not a separately-caused phenomenon.

**Going forward, not retroactively fixable for already-run scenarios:** any
new skill test in this project should measure the `without_skill` baseline at
n=3 first, and only proceed to design a `with_skill` comparison if that
baseline scores below 50% — otherwise redesign the scenario before spending
anything on the paired condition.

## Boundary note

This analysis strengthens the honesty of the existing self-audit; it does not
retire any of its other open items (single model, no oracle verification, no
third-party replication — see `README.md`). It also does not change any
skill's status label (WINS/TIE/LOSES/OPEN) in this project's existing
reports — those labels were never claimed to be statistically significant,
and this document is what makes that limitation checkable rather than
asserted.
