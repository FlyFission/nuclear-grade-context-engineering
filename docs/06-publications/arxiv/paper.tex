\begin{abstract}
AI coding agents can change software, choose tests, summarize results, and write the review used to accept their own work. These steps can occur in one coupled process. Existing controls often address self-modification, where an actor edits the gate meant to constrain it. They do not always address \emph{evidence self-authorship}. In that failure mode, the gate stays protected, but the actor writes the evidence it consumes. A confident hallucination can clear every gate for which it also wrote the input.

This paper treats acceptance of agent-assisted changes as a problem distinct from task performance. It defines an agent-specific form of evidence self-authorship and a five-axis profile for actor--evidence coupling. The axes are actor, context, mechanism, authority, and resource. The profile is not a score. Instead, an external, versioned policy can set evidence requirements based on consequence. The proposal adapts established review, configuration-management, verification, and assurance practice. A Git-native reference implementation shows that custody labels, coupling profiles, and decision state can be recorded, exercised, and checked for structural consistency. Those checks do not prove identity, truth, or independence. A twelve-scenario formative inspection supports design changes, not efficacy claims. The paper also states a falsifiable prediction and proposes a preregistered comparison of actor-controlled evidence with a defined separated-evidence condition.
\end{abstract}

\noindent\textbf{Keywords:} coding agents; AI-assisted software engineering; evidence custody; actor--evidence coupling; independent review; configuration management; software assurance.

\section{Introduction}
\label{sec:introduction}

Coding agents now do much more than complete code. In one session, an agent may inspect a repository, interpret requirements, edit source and prompts, change dependencies, run tools, choose tests, write a review, and recommend release. This concentration of work is productive, but it also creates a control problem. If the agent misunderstands the task, the same error can spread through the change, the selected evidence, the review narrative, and the release recommendation. The result may be internally coherent but still wrong.

Most context-engineering guidance aims to improve task performance. It helps agents select useful instructions, retrieve knowledge, use tools, retain state, compress long histories, and work through effective interfaces \citep{mei2025context,anthropic2025context,yang2024sweagent}. Those mechanisms are necessary. They do not, by themselves, answer five acceptance questions:

\begin{enumerate}
  \item What was the agent authorized to change or execute?
  \item Which claims must be true before the change is accepted?
  \item Who or what produced the evidence supporting those claims?
  \item Which decision does the evidence support?
  \item Which accepted state must remain under configuration control?
\end{enumerate}

We call the information needed to answer those questions \emph{context for accountable acceptance}. It does not replace context that helps an agent perform a task. It serves a narrower purpose: trust-bearing decisions. These decisions affect users, persistent data, money, permissions, external systems, public claims, release state, or other protected outcomes.

This paper presents \emph{graded accountable acceptance} through the open \method{} reference implementation \citep{flyfission2026repo}. The project uses ``nuclear-grade'' to describe an engineering posture with roots in public high-consequence practice. The term does not claim regulatory status, safety classification, formal assurance, or proven efficacy.

\subsection{Contributions}

The paper makes one problem-formulation contribution, one modeling contribution, and one implementation contribution:

\begin{enumerate}
  \item \textbf{Evidence self-authorship formulation.} The paper applies established self-review concerns to agent-assisted software acceptance. It separates gate self-modification from control of the evidence path. The formulation predicts lower reviewer detection when a change actor produces a plausible but wrong change and also controls the decisive evidence. The prediction is falsified if controlled studies find no meaningful difference, or if protected gates keep acceptance error within the same stated bound.
  \item \textbf{Actor--evidence coupling profile.} The paper defines five axes: actor, context, mechanism, authority, and resource. The axes expose correlated failure that role names can hide. An external consequence policy may limit coupling for decisive evidence, but the axes do not form an assurance ladder or one score. This paper does not set universal minimum profiles. Those choices belong in versioned policy outside the candidate's writable record.
  \item \textbf{Open reference implementation.} The repository shows that custody labels, coupling profiles, and decision state can be recorded with ordinary artifacts, exercised, and checked for structural consistency. These checks expose declared relationships. They do not authenticate identity, prove semantic adequacy or independence, or decide whether a profile meets a consequence policy. Lifecycle stages, packet files, risk tiers, verdict/apply-clearance, and templates remain implementation tools rather than separate research contributions.
\end{enumerate}

The work does not claim invention of configuration management, independent verification, governed context, assurance cases, professional self-review, human approval gates, or operational decision authority. It offers a narrow agent-specific synthesis around evidence custody and coupling in software acceptance.

\section{Background and Related Work}
\label{sec:related}

\subsection{Context, repository instructions, and agent harnesses}

Context engineering includes retrieval, memory, tool use, state management, history compression, and evaluation \citep{mei2025context}. Anthropic recommends small, high-signal context, retrieval when needed, progressive disclosure, and structured state \citep{anthropic2025context}. Repository files such as \code{AGENTS.md} provide standing instructions that work across tools \citep{agentsmd2025}. Spec Kit and similar workflows treat specifications, plans, and task records as direct inputs to coding agents \citep{github2026speckit,medin2025context}.

Harnesses for long-running agents preserve progress, use Git history, work in small steps, and require end-to-end checks \citep{anthropic2025harness}. OpenAI also describes the repository as the system of record. Its account emphasizes concise instructions, mechanical documentation checks, enforceable architecture, isolated worktrees, observability, and agent-to-agent review \citep{openai2026harness}. SWE-agent shows that the interface between an agent and its computer affects navigation, editing, testing, and task performance \citep{yang2024sweagent}.

This work is established prior art for repository legibility, durable state, specifications, executable feedback, and harness design. \method{} adds a layer for acceptance decisions. That layer records authority, controlled surfaces, evidence duties, provenance, decision rights, residual risk, and closure state.

\subsection{Evaluation integrity}

SWE-bench Verified used tasks screened by humans and tests kept outside the solving agent. It is a benchmark-level example of separating the solver from its evidence \citep{openai2024swebench}. OpenAI later stopped using the benchmark for frontier-model evaluation because contamination and flawed tests had weakened the judge \citep{openai2026noswebench}. The sequence shows an important limit. Independent execution does not make evidence valid when the evaluator, data, or environment has degraded. Actor--evidence independence is one control, not proof of correctness.

Research on repository instruction files gives a similar warning about context. In the settings they studied, Gloaguen \etal{} found that \code{AGENTS.md}-style files did not generally improve task success and did increase inference cost \citep{gloaguen2026agents}. The design lesson here is subtraction. Standing instructions should contain unusual constraints and exact routes. Deeper material should load only when needed.

Professional independence and model-evaluation research are closer to this paper's central failure mode. The IESBA Code defines a self-review threat as judging or relying on one's own prior work \citep{iesba2026code}. LLM evaluators can recognize and favor their own generations. Related generator and judge models can also show preference leakage through inheritance or shared model families \citep{panickssery2024evaluators,li2025preference}. Human-factors research separates proper automation use from misuse, disuse, and abuse. It also documents automation bias in decisions \citep{parasuraman1997automation,skitka1999automation}.

This paper does not claim to have discovered self-review or automation bias. It applies those concerns to agent-assisted software acceptance. The scope includes tests, summaries, omissions, risk framing, and claims used in a software-change decision.

\subsection{Configuration management, independence, and assurance reasoning}

Configuration identification, change control, status accounting, baselines, assessment, and controlled acceptance are established disciplines \citep{doe2016cm,nrc2013rg169}. Secure-software and AI-risk frameworks also require protected artifacts, provenance, governance, and risk management. They do not, by themselves, set rules for separating coding agents from acceptance evidence \citep{nist2022ssdf,nist2023airmf}.

NASA and NRC guidance treat independent verification, validation, review, and audit as lifecycle practices \citep{nasa2022swe141,nasa2022assurance,nrc2013rg168}. NIST guidance addresses separation of duties and independent assessment evidence \citep{nist2022assessment}. Tool accreditation and intended-use reasoning are also established ideas \citep{nasa2022swe136}.

Claims, arguments, and evidence are mature assurance concepts \citep{nist2022systems,omg2023sacm}. Recent work applies safety-case reasoning to frontier AI and uses language models to help find defeaters \citep{buhl2024safetycases,gohar2024codefeater}. \method{} does not replace a formal assurance case. It uses a thin repository-native chain: basis $\rightarrow$ claim $\rightarrow$ control $\rightarrow$ evidence or gap $\rightarrow$ decision.

Public guidance for high-consequence work also covers graded rigor, questioning assumptions, self-checking, peer checking, independent verification, turnover, and operational learning \citep{doe2009hpi}. This paper adapts those ideas to software agents. It does not import regulatory classes or claim that the domains are equivalent.

\subsection{Adjacent acceptance, governance, and provenance work}

Software Delegation Contracts provide the closest empirical comparison for coding agents. They organize work around a task, bounded authority, a returned work package, and an acceptance context. In a controlled pilot, 64 agent runs produced materials for 192 condition-blinded model reviews. The study reported better reviewability, not better correctness, with higher token use and wall-clock time \citep{schmalbach2026contracts}. Artifact-gate research also compares prompt-to-code, specification-driven, and artifact-aware delivery. It uses synthetic tasks and deterministic evaluators \citep{ravuru2026artifact}. These studies make broad claims about evidence bundles, artifact gates, and reviewability. This paper instead asks who controls the decisive evidence.

Governed AI-Assisted Engineering proposes human oversight that grows with regulatory impact, customer proximity, reversibility, and data sensitivity. It also requires evidence artifacts \citep{kang2026gaie}. This overlaps the paper's consequence grading, so no novelty is claimed for oversight tiers. ContextNest governs knowledge through version identity, provenance, integrity, approval state, and point-in-time reconstruction \citep{sulpovar2026contextnest}. Xu \etal{} propose a persistent context layer with access control, provenance, traceability, and human verification roles \citep{xu2025everything}. These systems govern which context an agent may use. This paper focuses on evidence and authority when a candidate software state is accepted.

Runtime Governance for AI Agents applies policy to agent identity, partial execution path, proposed action, and organizational state \citep{kaptein2026runtime}. AgentBound combines delegated authorization, behavioral rules, and site action contracts before execution. It also emits governance receipts \citep{kaul2026agentbound}. These systems are close to apply-clearance and authority surfaces.

Wang \etal{} connect claims, evidence, tool output, memory, actions, and outcomes in a process-accountability graph \citep{wang2026traces}. Zhang and Sun's Knowledge-Based Pull Requests separate acceptance of knowledge from integration of code across a trust boundary \citep{zhang2026kpr}. This body of work prevents broad novelty claims about governed context, evidence bundles, provenance, graded oversight, runtime authorization, or decision separation.

Two review-focused studies further narrow the contribution. Pollner treats AI-generated test artifacts as candidates that need risk-scaled human acceptance, not as self-validating evidence \citep{pollner2026oversight}. Ming \etal{} organize intent, success criteria, actions, completion claims, evidence, gaps, and rework constraints into a reviewable claim structure. Their controlled materials showed better detection of hidden gaps between intent and completion \citep{ming2026reviewability}. The acceptance-record schema in this paper is therefore an implementation tool, not an invention claim.

Industrial prior art is also substantial. Palantir's Ontology connects semantic objects to governed actions. Ontology proposals support review and approval. Scenarios remain hypothetical until their actions are applied under validation and permission controls \citep{palantir2026ontology,palantir2026proposals,palantir2026scenarios}. These capabilities prevent novelty claims about operational ontologies, controlled proposal and merge workflows, or separation of modeled state from authority to apply it. The remaining distinction is whether the candidate actor also controls the decisive evidence path.

The paper's specialization is narrow: an agent-specific and falsifiable form of evidence self-authorship; a five-axis coupling profile; a consequence-dependent admissibility proposal; and an open Git-native reference pattern. \Cref{tab:boundary} summarizes that boundary.

\section{Problem Formulation}
\label{sec:problem}

\subsection{Trust-bearing changes}

Let $c$ be a candidate change to code, configuration, prompts, models, permissions, data policy, tests, or release state. A change is \emph{trust-bearing} when acceptance commits an organization to an externally meaningful state or one that is hard to reverse. Examples include wider agent permissions, a changed payment path, a new data-retention rule, a new model or evaluation baseline, and a published assurance claim.

Acceptance requires more than a successful run. The method uses an \emph{acceptance-record schema} with eight fields: intent; discovered state; authority; claims; evidence and provenance; verdict and residual-risk disposition; accepted baseline; and revalidation or operational triggers. This schema is a record, not a proof system.

Let $\pi$ be a versioned consequence policy kept outside the candidate record. For consequence class $k$, acceptance requires four conditions. The required fields for $k$ must be present. Each decisive claim must have evidence whose coupling profile satisfies $\pi(k)$. Any open gap must have an authorized disposition. The actor issuing the verdict must have acceptance authority. Application also requires current apply-clearance.

This paper proposes that predicate but does not define one universal $\pi$. Each organization must state and protect its required profiles, decisive-claim rules, exceptions, and expected packet mode. Those rules must stay outside any surface the change actor can rewrite. A baseline loses reliance when a recorded trigger occurs, its evidence expires, or a behavior-driving surface moves outside the accepted envelope. These rules make missing records and invalid transitions visible. They do not provide mathematical assurance.

\subsection{The evidence self-authorship failure mode}

Two related failure modes must be separated:

\begin{description}
  \item[Self-modification.] The actor can edit the control, test, policy, or threshold intended to constrain it.
  \item[Evidence self-authorship.] The actor cannot edit the gate but can author all evidence, summaries, risk framing, and conclusions consumed by that gate.
\end{description}

We use \emph{evidence custody} to mean effective control over an evidence item. That control can cover generation, selection, transformation, execution environment, retention, and presentation. Provenance may show where an artifact came from without showing who controlled those choices. Custody exposes that control path.

Locking a gate addresses self-modification. It does not address evidence self-authorship. An agent can leave a protected CI rule unchanged while choosing favorable tests, summarizing incomplete output, omitting a failed condition, or writing the review narrative. The gate is structurally separate, but its information path remains coupled to the actor.

The central failure claim is therefore:

\begin{quote}
A confident hallucination can clear every gate for which it also wrote the input.
\end{quote}

This is not a claim that every agent-generated report is unreliable. Actor evidence is often useful and inexpensive. The point is that its provenance must be visible, and the required independence should scale with consequence.

\subsection{Threat model and control boundaries}

The main threat is a well-intentioned but fallible actor, not a malicious one. The actor produces a wrong change and a coherent explanation that repeats the same mistake. Evidence separation addresses shared reasoning errors, selective testing, persuasive omission, and unsupported confidence. It does not stop malicious behavior by itself.

Other threats need other controls. Locked surfaces and least privilege address unauthorized changes and prompt-injected or compromised actors. Protected baselines address stale or hidden configuration changes. Authenticated provenance addresses forged identity or rewritten evidence. Apply-clearance addresses changes in approvals, maintenance windows, external state, and rollback options after technical acceptance. Human review adds judgment, but it can fail through weak skill, incentives, limited time, or rubber-stamping. A compromised toolchain or colluding authority can defeat the pattern. High-consequence deployments therefore need controls outside the actor's administrative domain.

\section{Implementation Vehicle: The Graded Acceptance Method}
\label{sec:method}

The coupling profile in \Cref{sec:independence} is the modeling contribution. This section introduces the terms needed to show where that profile enters acceptance. The lifecycle, modes, packet files, and operating envelope are implementation tools.

\subsection{Lifecycle}

The full lifecycle is

\begin{center}
\textsc{Question $\rightarrow$ Discover $\rightarrow$ Specify $\rightarrow$ Plan $\rightarrow$ Execute $\rightarrow$ Verify $\rightarrow$ Review $\rightarrow$ Decide $\rightarrow$ Baseline $\rightarrow$ Operate $\rightarrow$ Learn}.
\end{center}

The lifecycle describes information flow. It is not a meeting schedule or a research contribution. A small change may cover several stages in a few lines. Detailed mnemonics and role prompts remain in the reference repository.

The operating principle is \emph{fast exploration, slow acceptance}. Agents may explore alternatives rapidly in a bounded workspace. A candidate becomes trust-bearing only when it is proposed for acceptance, release, application, or public reliance. Evidence and independence increase at that boundary.

A method becomes wasteful if it imposes the same ceremony on every change. \Cref{tab:modes} defines four levels. Teams select a mode based on authority, consequence, uncertainty, reversibility, and external trust. Diff size alone is not enough.

Tripwires move a change upward when it creates a trust boundary, irreversible action, destructive migration, wider permission, external claim, silent failure path, or material uncertainty. The method also permits a lower mode when consequence and proof remain small. If mode or profile rules are mandatory, a protected policy owner must define the tripwires, expected mode, and $\pi(k)$. Those rules must stay outside the candidate packet. A packet-local marker or PR-controlled validator cannot protect itself from downgrade.

\subsection{Change packets and context packs}

The Git-native unit is a change packet at

\begin{center}
\code{.nuclear/changes/<change-slug>/}.
\end{center}

A Standard packet uses six Markdown files for one acceptance record. They cover risk and consequence; basis and claims; bounded plan and authority; trace links; verification and provenance; and the final decision. The final file also records residual risk, rollback, monitoring, and baseline triggers. The filenames aid repository use. They are not separate research constructs.

The packet does not replace issues, pull requests, tests, CI, or operations systems. It links those primary artifacts around one decision and favors links over copied output. Its task-specific view gives an agent only what the current phase needs. That includes the objective, authority, evidence duties, stop conditions, source lineage, and open gaps. The packet has failed when it becomes a repository summary, repeated narrative, or AI-generated paperwork that no reviewer uses.

\subsection{Controlled agent operating envelopes}

Agent behavior depends on more than source code. The controlled configuration boundary may include prompts, model identifiers and settings, tool schemas, permissions, credential policy, evaluation cases, scoring rules, skills, retrieval rules, memory, context packs, and approval instructions. We call this the \emph{agent operating envelope}.

The term does not imply a formally qualified tool. It identifies behavior-driving surfaces that need version control and new checks when an organization relies on them. A useful baseline records accepted versions, intended use, supporting evidence, known limits, open gaps, and triggers for a new check. This applies established configuration-management and intended-use reasoning to software agents \citep{doe2016cm,nasa2022swe136}.

\section{Actor--Evidence Coupling and Independence}
\label{sec:independence}

Independence is not a yes-or-no label. A different process, agent name, or model call may still use the same prompt, retrieved material, orchestrator, scoring rule, and budget. A new reviewer label does not create a new evidence path. The key question is whether the evidence path can fail in a different way from the implementation path.

Each evidence item receives a five-axis profile $P=(a,c,m,u,r)$:

\begin{enumerate}
  \item \textbf{actor ($a$)}: did a different actor perform or witness the check?
  \item \textbf{context ($c$)}: did the verifier reconstruct the problem without accepting the actor's narrative as fact?
  \item \textbf{mechanism ($m$)}: did the check use a different test, oracle, model family, tool, or human technique?
  \item \textbf{authority ($u$)}: was the actor unable to redefine the scope, threshold, evidence requirement, or verdict?
  \item \textbf{resource ($r$)}: was the actor unable to starve the verification budget or suppress its output?
\end{enumerate}

Each axis is labeled \emph{coupled}, \emph{partially separated}, or \emph{separated}. The record also gives a short basis for the label. These axes are analytic views, not separate causes. One shared orchestrator, prompt, budget, or policy owner may couple several axes at once. The basis should name those shared dependencies. Future evidence may support more axes.

The resulting profiles form a partial order, not a numeric score. For example, a human witness does not always provide stronger evidence than a diverse mechanical check. A different model can also remain coupled through shared context or authority. An external, versioned consequence policy may set limits for decisive claims. This paper does not define a universal ladder or one universal policy $\pi$.

\section{Authority and Decision State}
\label{sec:authority}

\subsection{Surface classification}

Agent authority should be defined over surfaces, not only actions. The method uses four practical classes:

\begin{description}
  \item[Writable.] The actor may modify the surface within scope.
  \item[Locked.] The actor may read but not modify the surface.
  \item[Append-only.] The actor may add evidence or events but may not rewrite prior records.
  \item[Human-controlled.] A named human or policy owner must authorize the action or state transition.
\end{description}

A coding agent may be allowed to write implementation files while CI policy, permission allowlists, release criteria, and acceptance records remain locked or human-controlled. For unattended operation, ``ask first'' is not a runtime control. The enforceable form is \emph{block, record, and escalate}.

\subsection{Plan authority, build authority, and acceptance authority}

Authority to propose a plan is not authority to execute it. Authority to execute a plan is not authority to accept the resulting state. A decision-rights record identifies who may propose, build, verify, review, accept risk, baseline, release, apply, and publish. Combining roles may be reasonable for low-consequence work, but the combination should be explicit.

\subsection{Verdict and apply-clearance}

A release \verdict{} answers:

\begin{quote}
Does the admitted evidence justify relying on this exact candidate for the stated purpose and conditions?
\end{quote}

\applyclearance{} answers:

\begin{quote}
May this accepted change be applied now, under the current approvals, external state, maintenance window, and operational policy?
\end{quote}

The states often coincide in ordinary software and diverge in consequential operation. A freeze window may close, an approval may lapse, external state may change after verification, or a rollback route may become unavailable. A technically accepted change can therefore lack present authorization for application. Authority separation, operational decision rights, runtime mediation, and scenario/apply distinctions are established or adjacent practice \citep{nasa2024models,doe2016cm,kawas2026decision,kaul2026agentbound,palantir2026scenarios}. Their role here is implementation clarity, not standalone novelty.

\section{Git-Native Implementation}
\label{sec:implementation}

The public reference implementation described here was assessed at repository commit \code{92357cd} \citep{flyfission2026repo}. Its pre-change baseline was commit \code{7144831}. The assessed revision contains:

\begin{itemize}
  \item canonical lifecycle, mode, authority, evidence-custody/coupling, configuration, and source-foundation documents;
  \item Quick, Standard, and optional stronger templates;
  \item reusable agent skills with triggers, inputs, outputs, verification, and stop rules;
  \item command prompts and role instructions for Plan, Run, Observe, Verdict, and Educate stages;
  \item starter kits for partial adoption;
  \item a Python package and command-line interface;
  \item a structural validator, repository doctor, token-budget audit, and efficacy signal checker;
  \item tests, continuous integration, worked examples, citation metadata, and disclaimer boundaries.
\end{itemize}

The validator checks packet structure, links, status values, placeholders, declared custody relationships, coupling profiles, and boundary wording. It does not decide whether an engineering claim is true. It also does not assign consequence, choose decisive claims, or decide whether a profile satisfies $\pi(k)$. Structural checks can expose a missing evidence field or an internal contradiction. They cannot replace engineering judgment. Mandatory enforcement needs three protected inputs outside the candidate's writable tree: a pinned validator, the expected mode, and a versioned consequence policy.

The assessed commit was also run from a clean archive. The exact commit-relative commands were \code{python -m pytest -q}, which passed 212 tests; \code{python -m ruff check .}; \code{python tools/ng.py doctor .}; \code{python tools/ng.py tokens .}; and \code{python tools/ng.py eval .}. The evaluation reported 25 of 25 selected decision signals across five executable cases.

Strict checks used \code{python tools/ng.py validate}, followed by the packet path and \code{--strict-custody}. The first packet path was
\begin{quote}
\small\path{.nuclear/changes/white-paper-draft}.
\end{quote}
The second was formed without whitespace by concatenating
\begin{quote}
\small\path{docs/03-worked-examples/ai-agent-tool-permissions/}\\[-0.3em]
\path{.nuclear/changes/add-agent-tool-permissions}.
\end{quote}
Both strict commands passed. These results show bounded executability and structural consistency. They do not establish claim truth, policy quality, authenticated independence, or effectiveness.

The implementation uses Markdown and Git so its records can outlive a model, coding agent, editor, or orchestration framework. Tool-specific integration may improve use, but the accepted claim, primary evidence link, and decision should not disappear when a chat ends or an API changes.

The repository also treats context volume as a failure surface that can be measured. Always-loaded instructions stay short. Deeper skill content loads only when its trigger fires. Token audits identify instruction growth. The method rejects records that do not change execution, evidence, review, decision, or operational learning.

\subsection{Git and evidence trust model}

Git-native does not mean immutable, authenticated, append-only, or independent. Trust in an acceptance record depends on who controls the repository, branch policy, CI identity, evidence store, signing keys, and history. In-toto calls its authorized actors functionaries and links their supply-chain steps. SLSA separates provenance made in a trusted control plane from metadata that user-controlled build steps can change \citep{intoto2026,slsa2026}. The implementation can link to those attestations, but it does not recreate their guarantees.

\section{Formative Design Inspection}
\label{sec:evaluation}

\subsection{Research questions}

The current evaluation addresses two limited questions:

\begin{description}
  \item[RQ1.] Do author-constructed scenarios show more explicit decision signals than a reasonable direct-prompt path? Where does the method add needless overhead?
  \item[RQ2.] Does a deterministic regression harness retain selected decision signals in worked artifacts?
\end{description}

Neither question measures production defects, safety, reviewer accuracy, task completion, or organizational outcome.

\subsection{Twelve-scenario artifact comparison}

The repository contains twelve paired scenarios. Six cover development changes: a tiny README fix, an agent workspace boundary, a dependency update, public assurance wording, a prompt/model baseline, and an agent handoff. Six cover operational or public risks: payment-webhook idempotency, a data-retention migration, a release cut, an incident regression, external API permission, and a source-citation adoption document. Each pair compares a reasonable simple-prompt artifact with the method's records for the same scenario.

The author scored each artifact from one to five on decision clarity, hidden-risk discovery, evidence quality, and ship/defer usefulness. Overhead was scored separately. The scenarios, artifacts, rubric, and scores were all author-produced. There was no blinding or independent rating. The paper therefore reports patterns instead of numerical means. Raw scores remain in the public evaluation directory.

The inspection produced three design hypotheses:

\begin{enumerate}
  \item On the tiny documentation fix, the method added overhead without changing the decision. This result supports a legitimate Administrative floor and Quick mode.
  \item Scenarios involving authority, data, payment, model/prompt baselines, release, or public claims appeared to expose decision details that direct prompts left implicit. These details included rollback routes, credential scope, silent failure paths, and ownership of residual risk.
  \item The largest author-scored gap involved hidden-risk discovery. This dimension faces the greatest confirmation risk because the author knew the seeded concerns.
\end{enumerate}

These hypotheses shaped the tripwires, mode boundaries, and worked example. They remain untested on artifacts designed by independent researchers. They are formative design feedback, not evidence of better decisions or software outcomes. Studies of delegation contracts, artifact gates, and intent-based claim review provide stronger evidence for reviewability and evidence organization. None validates this method's coupling prediction \citep{schmalbach2026contracts,ravuru2026artifact,ming2026reviewability}.

Under the paper's own model, the scenarios, scores, manuscript synthesis, and AI-assisted drafting are actor-controlled evidence. Disclosure makes their custody visible, but it does not make them independent. Comments from several model providers informed revision. Those comments remain advisory model judgments, not peer review or independent empirical verification.

\subsection{Signal-presence harness}

A deterministic harness checks selected artifacts for required decision signals. These signals include bounded file-write authority, adversarial proof claims, source-lineage boundaries, credential scope, rollback, monitoring, and ownership of residual risk. The harness prevents examples from silently losing named fields. It does not judge whether the fields are adequate. It also does not automate the direct-prompt comparison.

\subsection{Evidence supported by the current repository}

The current evidence supports five bounded statements:

\begin{enumerate}
  \item the method can be represented as reusable repository artifacts;
  \item the implementation is runnable and testable;
  \item the worked example demonstrates one complete claim-to-evidence path and visible gaps;
  \item the scenarios illustrate the method's intended use and overhead boundary; and
  \item the harness can preserve selected decision signals against regression.
\end{enumerate}

Claims about decision effectiveness, correctness, defects, or organizational outcomes require independent study.

\section{Adoption and Operational Cost}
\label{sec:adoption}

The adoption unit should be a decision problem, not the whole repository. A team begins by asking what could fail silently, what would be hard to reverse, who owns acceptance, and what evidence would change the decision. The smallest mode that answers those questions is preferred.

Quick mode should remain visibly legitimate. If a local, reversible change has obvious proof and no new trust boundary, a full Standard packet is waste. Standard or stronger modes become useful when a change affects data, money, permissions, dependencies, agent authority, model/prompt baselines, release posture, external actions, or public trust claims.

The method creates real costs: writing and reviewing records, retaining evidence, rerunning checks, managing baselines, and maintaining role boundaries. Independence also consumes time and compute. Those costs should be compared with the cost of omitted authority, hidden evidence gaps, rollback failure, or a misapplied action. The method should be removed or simplified when its records do not improve a decision.

The method can fail by accretion. Additional templates, taxonomies, gates, and standing instructions may create the context noise they were meant to control. Subtraction is therefore an operating requirement. A record remains only if it changes execution, evidence, review, decision, or learning.

\section{Limitations and Threats to Validity}
\label{sec:limitations}

\subsection{Bounded novelty}

This paper claims a narrow agent-specific synthesis and implementation. Many parts have prior art. These include self-review, governed context, evidence bundles, artifact gates, graded oversight, claim--evidence structures, execution provenance, configuration control, independent assessment, operational ontologies, and authority separation.

The primary claims have sharper failure conditions. If controlled comparisons find no meaningful detection benefit from evidence separation, evidence self-authorship may be only a new label for established self-review. If the coupling profile exposes no more correlated failure than role labels or gate protection, it may be only a checklist. The implementation could retain descriptive value even if those predictions fail.

\subsection{Author involvement and confirmation risk}

The author developed the method, designed the twelve scenarios, produced or curated the artifacts, and assigned the scores. The project also defined the signal-presence harness. This creates confirmation and selection risk. Public artifacts make the reasoning inspectable but do not make it independent.

\subsection{Artifact quality is not outcome quality}

A complete change record may improve a reviewer's decision without improving the implementation. A poor record may accompany correct code. Future work must measure reviewer accuracy, omission detection, review time, token cost, task outcome, escaped defects, rollback quality, and operational behavior.

\subsection{Simulated independence}

Separate agents can share a model family, prompt, retrieved context, orchestrator, rubric, and budget. This reduces direct coupling while preserving common-cause failure. Role names such as ``reviewer'' and ``judge'' are not evidence of technical, managerial, resource, or authority independence.

\subsection{Human gates can rubber-stamp}

A human owner is not a guarantee. Review quality depends on competence, time, incentives, authority, primary-evidence access, and willingness to block. The method can make these conditions visible but cannot manufacture them.

\section{Research Agenda}
\label{sec:research}

\subsection{Falsification and study design}

The evidence self-authorship formulation makes a testable prediction. When an actor writes both a plausible but wrong change and the decisive evidence used by its gates, reviewers should detect errors less often than under a separated-evidence condition.

A preregistration must name the target profile on all five axes. It must also define a manipulation check before data collection. One defensible first test would separate the actor, verification mechanism, and verdict authority. It would prevent the change actor from vetoing or suppressing results. It would measure, rather than assume, the remaining context and resource coupling.

The study must define the smallest effect of interest and an equivalence or non-inferiority margin. A non-significant result does not prove equivalence. The formulation is weakened or falsified if a well-powered comparison places the effect inside the stated equivalence region. It is also weakened if locked thresholds and protected CI keep acceptance error within the same prespecified margin as the separated-evidence condition.

A credible test should keep method design separate from task design, execution, scoring, and publication. We propose three matched conditions: a direct-prompt workflow; a contract or artifact-bundle workflow with actor-authored evidence; and the same structured workflow with the preregistered separated-evidence profile and manipulation check. The study should cross these conditions with low- and high-consequence scenarios that contain plausible seeded defects.

Artifacts should be randomized and blinded. Independent reviewers should score defect detection, omission detection, false acceptance, evidence quality, review time, and confidence calibration. Research on automation use and automation bias should guide reviewer instructions and reliance measures \citep{parasuraman1997automation,skitka1999automation}. The study should publish its prompts, models, tools, artifacts, rubrics, failures, and negative results.

\subsection{Secondary questions}

The study should also ask:

\begin{itemize}
  \item which profile axes carry any observed effect;
  \item when nominally separate agents remain too correlated;
  \item whether graded rigor controls cost without burdening small changes;
  \item which behavior-driving changes require revalidation;
  \item whether reviewers distinguish verdict from apply-clearance when external state changes; and
  \item how often records become empty ceremony.
\end{itemize}

Field studies should report bypasses, abandoned records, false alarms, accepted residual risks, and cases where the direct path performs better. A method about evidence should publish its own failures.

\section{Conclusion}
\label{sec:conclusion}

A protected gate is not independent when the change actor controls every decisive input it consumes. That control may include how evidence is generated, selected, changed, retained, or presented. Evidence self-authorship is an agent-specific form of self-review. Evidence custody makes the control path visible.

The central prediction is testable. Reviewers should detect plausible but wrong changes more often under a preregistered separated-evidence condition than under an otherwise matched actor-controlled condition. The study must state which axes it separates and how it will check that separation. Whether the effect exists, and which axes matter, remains an open empirical question.

This paper turns the problem into custody labels, a five-axis coupling profile, a consequence-dependent admissibility proposal, and an acceptance-record schema. The \method{} repository shows that ordinary Git workflows can record these declarations and check their structure. The checks reveal declared relationships. They do not authenticate identity, prove semantic adequacy, establish independence, or decide whether a profile is admissible. Lifecycle, risk modes, verdict/apply-clearance, and baselines remain implementation tools. The trust model also makes clear that Git alone does not authenticate evidence or establish independence.

The current inspection is formative and author-produced. The defensible result is a problem formulation, a control pattern, and a runnable reference implementation. It is not a claim of improved correctness or assurance. Independent, blinded evaluation is the next gate for the central prediction.
